# Turning AuditScope proofs into legible assurance

> Research review of the first version of [the Lean scope plan](2026-11-09-lean-scope.md) (commit `07a7188`). The plan has since been updated with these recommendations. Property and step numbers below refer to that first version. The assumptions A1–A10 here are not the A1–A7 of the step 1 code map; the updated plan lists both.

The plan follows the strongest current precedent closely: Kiro's November 2026 Lean study of agent harnesses and AWS Cedar's verification-guided development. Even so, as written, all four theorems could be proved while the intended property fails in the Python. That property is "the auditor cannot change what an out-of-scope agent sees or does". Most of the value comes from three changes to the statements. **Property 2 should be a frame theorem over a per-agent `view` defined independently of `affected`**; this alone settles the `AmendPending` and `Halt` questions. **Property 3 should be a trace invariant that ties each check to the exact (op, world) pair that `apply` consumes**, including replay and post-rollback worlds. **A new authority-confinement property should say that no step changes or widens the scope**; without it, Property 4 is only a fact about static values. The next priority is the Python boundary. Published studies of verified systems find **most bugs in the shim around the proofs, not in the proofs themselves (11 of 16 in Fonseca et al.)**. The plan's differential tests compare only `problem` and `affected`, so `apply` effects and the controller's apply sites, which are what Properties 2 and 3 are about, are linked to the code only by a human reading it. Third, the proofs will be AI-written. The model definitions and theorem statements should therefore be frozen in a human-reviewed challenge file, and proofs should be gated by an axiom allow-list rather than a deny-list, because the way Lean reports native computation changed during 2026. The result should be published as a two-tier claim: kernel-checked theorems about a model at a pinned commit, plus correspondence to the Python that is tested but not proved. It should come with a numbered list of assumptions and explicit non-guarantees, in the style of seL4 and Kiro. The research found no earlier mechanised verification of the permission layer of an AI evaluation or auditing harness, so done this way the work would be a first of its kind.

## The plan already follows the strongest 2026 precedent

The plan's direct template is **Kiro's "Harness properties in Lean" (Kharkov, Erata, Omidvar-Tehrani, Mukherjee; 2 Nov 2026)**. That work modelled 26 functions across TypeScript, Rust and Python harness code. Each model was a pure Lean function with a file:line header. Of **96 candidate properties, 70 were proved, 2 were bounded checks not counted as proofs, 18 were falsified and reproduced on unmodified code, and 6 were partial**. The models were linked to the real code by **97,938 differential cases with zero final mismatches** ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)). The plan copies the right parts: no Mathlib, one Lean definition per source function, human review of statements before any proof, vacuity witnesses, `bug_…` theorems, counting a finding only once it reproduces on unmodified code, and a deliberately broken copy to show the test harness can fail. The plan is **stricter than Kiro on native computation**: Kiro used `native_decide` in 17 theorems (none backing a proved property), and the plan bans it outright ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)). Kiro's permission theorems ("a sub-agent is never less restricted than its parent"; "tightening a policy never turns a refusal into an approval") have the same shape as Property 4. So do Progent's "monotonic confinement", where the action space "can only shrink without approval" ([Progent](https://arxiv.org/abs/2504.11703)), and Nucleus's PROVED rows for attenuation and monotonicity ([Nucleus](https://coproduct-opensource.github.io/nucleus/north-star.html)).

The architecture of a mirroring model plus differential tests is also how AWS built Cedar. "We prove properties about a readable formal model, and rigorously test that the deployed code matches that model." The executable Lean model serves as the specification, and Rust is compared against it by daily differential random testing (DRT) ([How We Built Cedar](https://arxiv.org/html/2407.01688v1)). Cedar's numbers set realistic expectations for this project. **Proofs found 4 bugs** (all in the validator, including a non-termination bug DRT was unlikely to hit), while **DRT and property-based testing found 21** ([How We Built Cedar](https://arxiv.org/html/2407.01688v1)). Much of the bug-finding value is therefore likely to come from writing the model and running the differential tests, and the proofs will catch what random sampling cannot. One discrepancy in the sources: the paper gives **1,673 LOC of Lean model, 5,714 LOC of proofs and 15,693 LOC of Rust**, while the AWS blog gives 24,915 lines of Rust, presumably because the two count differently ([AWS Open Source blog](https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development)). Either way, the model is roughly an order of magnitude smaller than the code it mirrors.

Treating LLM generation as an arbitrary function is the right threat model, and strictly it is a universal quantifier, not an assumption. The AI-control literature treats the untrusted model as a possibly deliberate saboteur and lets the red team substitute any policy for it ([Greenblatt et al.](https://arxiv.org/abs/2312.06942); [Games for AI Control](https://arxiv.org/abs/2409.07985)). Agent-security systems use the same premise: "Assume the agent is compromised. Constrain what it can do anyway. Prove the constraints hold" ([Nucleus](https://coproduct-opensource.github.io/nucleus/north-star.html)). With the auditor quantified this way, the theorem becomes a reference-monitor property that holds for every auditor, whether scripted or LLM, honest or adversarial, and whatever an `experiments/` override of `_dispatch` does. Any narrower assumption would turn the proof into an unverifiable claim about model behaviour.

The plan's "things to check first" all sit at representation boundaries, which is where the evidence says bugs cluster. Kiro reports that "most findings sit at a boundary between two representations" (UTF-16 vs bytes, paths vs globs) ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)). Cedar dropped a string-size operator from the language when the model and the code counted different units, and the Cedar *model itself* wrongly rejected "::" in IPv6 parsing ([How We Built Cedar](https://arxiv.org/html/2407.01688v1)). CompCert's PowerPC back-end issue came from a formal semantics that did not constrain an immediate's width ([Yang et al. PLDI'11](https://users.cs.utah.edu/~regehr/papers/pldi11-preprint.pdf)). `None` vs empty set, string op names and `recipients=None` are this project's equivalents. Finally, deferring the information-flow theorem follows seL4's order. seL4 proved integrity first ([Sewell et al. 2011](https://www.sel4.systems/Research/pdfs/sel4-enforces-integrity.pdf)) and noninterference two years later, reusing the integrity theorem as a lemma ([Murray et al. 2013](https://sel4.systems/Research/pdfs/sel4-from-general-purpose-to-proof-information-flow-enforcement.pdf)). The plan should keep that order, and write today's Property 2 so it can be reused the same way.

### Property 2 should be a frame theorem over a defined view

Property 2 currently says that every agent whose generation, context, deliveries or turns `apply` changes is in `affected`. The contrapositive is easier to state and harder to get wrong: for all `op w w' a`, `apply op w = .ok w' → a ∉ affected op w → view a w' = view a w`. This is **seL4's integrity theorem with the auditor as the only subject** ("State changes initiated by the subject are bounded by the policy") ([Brecknell, seL4 Summit 2022](https://www.sel4.systems/Summit/2022/slides/d1_04_Explaining_the_seL4_integrity_theorems_Matt_Brecknell.pdf)). It is also **Nickel's "local respect"**: "an action by a domain that cannot affect domain u leaves u's view unchanged" ([Nickel, OSDI'18](https://unsat.cs.washington.edu/papers/sigurbjarnarson-nickel.pdf)). In Dafny's terms, `affected` is a `modifies` clause, and anything it does not list is guaranteed unchanged ([Dafny FAQ](https://dafny.org/dafny/HowToFAQ/FAQModifiesThis)). The benefit is that completeness now rests on one reviewable definition, `view`, instead of a list of effect kinds that can silently miss one. With that definition in place, the plan's first suspected gap stops being a matter of inspection. If `AmendPending.agents()` lists only agents in the new steps, then any op that drops bob's pending turn without adding one changes `view bob`, and the theorem fails. A fix would set `affected` to the agents whose pending sequence differs, which is at least the union of agents in the old and new schedules.

**The definition of `view` is now the main risk to statement fidelity**, and it must be written as specification, not as mirror code. It has to include everything an agent's next LLM call can depend on: its context, message order and indices, pending deliveries, generation slots, and its turn schedule including positions. If `view` leaves out turn order, `AmendPending` passes trivially. Just as important, `view` and any `changedAgents w w'` helper must be defined from the modelled world state and never in terms of `affected`. Otherwise Property 2 is true by construction. This kind of definitional overfitting is what Fonseca et al. found in Chapar, where a client assertion checked its own if-condition and so always held ([Fonseca et al., EuroSys'17](https://www.cs.purdue.edu/homes/pfonseca/papers/eurosys2017-dsbugs.pdf)). This is why the plan's step 2 rule of "one definition per Python function" needs a second category. `view`, `changedAgents` and the trace log are *specification* definitions with no Python counterpart. They belong in a separate, reviewed file, and each needs a prose justification for why it is the right one.

### Halt, AmendPending and unknown ids need fail-safe answers, not silent passes

Under the frame form, `Halt` with no agents fails at once, because halting removes every agent's future turns and so changes every view. seL4 offers two honest ways out. **Round up**: seL4 conservatively treats unclassifiable authority as "conferring complete control over the target" ([Sewell et al. 2011](https://www.sel4.systems/Research/pdfs/sel4-enforces-integrity.pdf)). Here that means `affected Halt w = all agents`, so `agents={"alice"}` forbids Halt. **Explicit exception**: seL4 excludes its trusted resource manager from the integrity theorem by name ([Sewell et al. 2011](https://www.sel4.systems/Research/pdfs/sel4-enforces-integrity.pdf)). Here that means a named carve-out in the headline theorem, such as `op ≠ Halt ∨ scope.haltPermitted`, together with a line in the assurance statement. The round-up should be the default because it is sound and costs only usability. The exception is justified only if experiments genuinely need narrowly scoped auditors to halt runs. What cannot stay is the current situation, where `Halt` passes any agent limit by accident. That is also why the Cedar-style "default deny" lemma (`agents = some []` rejects any op with non-empty `affected`) does not cover Halt today: Halt's `affected` is empty ([Cedar, arXiv 2403.04651](https://arxiv.org/pdf/2403.04651)).

The third check-first item, an unknown message id with `recipients=None` falling back to `()`, is a **fail-open default**. It inverts Saltzer and Schroeder's principle that the "default situation is lack of access" ([Saltzer & Schroeder summary](https://carlstrom.com/stanford/quals/mirror/www.stanford.edu/~emrek/quals/summaries/The_Protection_of_Information_in_Computer_Systems-Saltzer-1975.txt)). The plan asks whether `apply` rejects such an op on every path. A stronger and more legible approach is to make it a theorem modelled on Cedar's "validation soundness" (a validated policy "will never result in a type error"): if `problem scope op w = none`, then `apply op w` is defined ([How We Built Cedar](https://arxiv.org/html/2407.01688v1)). That forces `problem` itself to reject the unknown id. The Python then no longer depends on every `apply` path happening to raise. More generally, an `affected` that cannot be computed should produce a problem, never an empty set. Empty sets from error paths are the "default means all, treated as none" inversion that the plan's representation list already warns about.

### Property 3 must bind each check to the world apply consumes

"The controller never applies an op for which `problem` is not `none`" can be proved in a weak form: some function calls `problem` before `apply`. That does not establish that the check and the effect concern the same op in the same world. Verified kernels avoid time-of-check-to-time-of-use (TOCTOU) gaps by putting the check and the effect in one atomic transition over one state. Nickel's traps "run atomically with interrupts disabled" and it "provides no guarantees in concurrent settings" ([Nickel](https://unsat.cs.washington.edu/papers/sigurbjarnarson-nickel.pdf)). seL4 states integrity as a relation between the pre-state and post-state of one kernel call ([Sewell et al. 2011](https://www.sel4.systems/Research/pdfs/sel4-enforces-integrity.pdf)). For this harness, the model should have exactly one world-mutating primitive, `applyRaw`, reachable only through `applyChecked`. Each application should append `(op, source, preWorld)` to a log, with `source ∈ {live, replay, rollbackIntervention}`. Property 3 then becomes an invariant proved by induction over all input sequences: `∀ gen auditor inputs, ∀ e ∈ (run gen auditor inputs).log, problem scope e.op e.pre = none`. This is the "always invoked" requirement of the Anderson report ([Anderson 1972](https://apps.dtic.mil/sti/pdfs/AD0758206.pdf)), stated over every reachable transition as verified kernels do.

Three consequences need checking against the Python, and each is a hypothesis until step 1's file:line map exists. **Replay** must re-run `problem` against the replay-time world and must not trust a recorded verdict. `affected` depends on `w`, through the `recipients=None` expansion and through `AmendPending`'s dropped turns, so the same op can have a different footprint after a code or scope change. **Rollback with interventions** must be checked in execution order: the rollback's own effect first, then i₁ in the branch world `w_b`, then i₂ in `w_b` after i₁, and so on. If `_rollback_problem` checks every intervention against the pre-rollback world, that is a TOCTOU bug, because an existing-message op can resolve to different recipients in the branch. This adds a new item to the plan's check-first list. **The rollback op itself** changes the view of every agent whose state differs between the current world and the branch point. Its `affected` must include those agents, in addition to the recursively checked interventions. Otherwise "roll back, then intervene within scope" can undo an out-of-scope agent's progress without any check. Property 1's phrase "recursively for rollback interventions" should also say which world each nested check uses.

The functional Lean model cannot exhibit the Python-only version of TOCTOU. If `ControlOp` instances are mutable (for example `AmendPending` holding a list of steps), in-process auditor code can change them after `problem()` returns and before `apply()` runs. Frozen dataclasses with tuple fields, or a deep copy taken at the check point, close this gap. Otherwise it has to appear as a stated assumption. If the controller ever runs auditor dispatch concurrently with agent turns under asyncio, the atomic-step assumption must be stated explicitly, as Nickel and Kiro do ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)).

### Property 4 needs a companion: nothing widens the scope

Monotone narrowing and exact intersection are necessary, but on their own they describe static scope values. seL4 pairs integrity with **authority confinement** (Theorem 2: "The property pas-refined pas is invariant over kernel calls"). In other words, the policy remains an upper bound on authority after every step ([Sewell et al. 2011](https://www.sel4.systems/Research/pdfs/sel4-enforces-integrity.pdf)). Brecknell adds that switching away from a trusted component "requires proof that it establishes a new well-formed policy" ([Brecknell 2022](https://www.sel4.systems/Summit/2022/slides/d1_04_Explaining_the_seL4_integrity_theorems_Matt_Brecknell.pdf)). Object-capability results say the same thing as "no authority amplification": a subject's authority can grow through interaction unless something forbids it ([Maffeis, Mitchell, Taly](https://spiral.imperial.ac.uk/bitstream/10044/1/95215/2/DTR10-6.pdf)). The plan should therefore add **Property 5**: across every controller step (live, replay, rollback or intervention), `scope_after = scope_before`, and any scope handed to a helper or nested auditor is `≤` its parent. This is Kiro's sub-agent theorem, and it is what the L2-helper composition actually depends on. One question for the Python is whether rollback snapshots include controller state that holds the scope.

The encoding should keep `none` as ⊤ exactly. Represent each component as `Option (List String)` with a `Bool` membership function. Define `s ≤ s'` by membership predicates, not by list equality, because deduplicated lists are not extensional. Prove `some [] ≤ none` and check that the reverse order is not derivable. State intersection as `allows (meet s t) op w ↔ allows s op w ∧ allows t op w`, proved through the rollback recursion as well. That iff holds only because `allows` is a conjunction of an ops test and an agents test evaluated on the same `affected op w`. There is also an expressivity limit to record now. A product of an op set and an agent set cannot express "ReplaceGeneration only on alice, Halt globally", and it is not closed under union. If the L2 + L1 composition needs per-(op, agent) policy, the scope becomes a relation and Property 4 has to be redone. Zelkova's question, "is policy A more permissive than B", is exactly what Property 4 should answer for the composed scope ([Zelkova, FMCAD'18](https://cs.utexas.edu/~hunt/FMCAD/FMCAD18/papers/paper3.pdf)).

## The Python boundary, not the proofs, is where defects will hide

The most reliable empirical finding in this literature is about *where* verified systems fail. Fonseca et al. studied IronFleet, Verdi and Chapar and found **16 bugs: 11 in the shim linking verified to unverified code, 2 in specifications, and the rest in verifier tooling**. None were in the verified protocols, despite more than eight months of searching. The paper itself is inconsistent about the tool count: Figure 3 says three, Section 6 says four. Their conclusion was that "verification, while beneficial, posits assumptions that must be tested" ([Fonseca et al.](https://www.cs.purdue.edu/homes/pfonseca/papers/eurosys2017-dsbugs.pdf)). AWS's Dafny authorization engine (AuthV2) shows the same pattern. Production shadow testing exposed **7 mismatches, "all from specification inaccuracies or incompleteness"**, and none came from the tools or proofs ([Chakarov et al., ICSE 2025](https://cdn.amazon.science/bb/40/22ac44f84f6d8eb625ac9666a00f/formally-verified-cloud-scale-authorization.pdf)). The extracted text reports agreement on "1015" samples, which probably means 10^15, but the extraction has not been confirmed. In this project the shim is the controller's apply path, the Python↔Lean JSON bridge, and any code that can touch the world without going through the controller.

### Differential tests must cover effects and apply sites, not just verdicts

Step 5 compares the Lean and Python versions of `problem` and `affected`. Property 2, however, rests on the Lean model of `apply`, and Property 3 rests on the Lean model of the controller. Neither is linked to the Python by anything except a reviewer reading the code. Kiro's method links input/output behaviour of pure functions, and most of Kiro's targets were that kind of function ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)). This plan's important properties are about effects and control flow instead. Three additions close the gap.

**Effect differential test.** Run each generated op through the Python `apply` on a generated world. Diff the per-agent view before and after, and compare the set of changed agents against both the Lean effect function and Python's own `affected`. This tests Property 2 directly on the real code, independently of the Lean model.

**Runtime assertion at the single apply primitive.** Across Hypothesis-generated *episodes* that include replay and rollback, assert at the apply primitive that `problem(op, world) is None` holds for the world actually passed in.

**Structural CI check.** Use an AST-based inventory of every call to `apply` and every assignment to world, message-store or schedule fields, compared against the step 1 file:line map. Add a test that fails when `ControlOp.__subclasses__()`, enumerated recursively, contains a class with no model entry. The Lean `Op` type is closed, but Python dispatch is not: an `experiments/` subclass can override `agents()`, `affected()` or `apply()`, or define a new op.

That last point settles the plan's "Confirm this" about `LLMAuditor._dispatch`. The confirmation to look for is that `_dispatch`, and every `experiments/` override, can only return op values and holds no reference to the world or controller. Anderson's report requires the mechanism to be "tamper proof", "always invoked" and "small enough to be subject to analysis and tests" ([Anderson 1972](https://apps.dtic.mil/sti/pdfs/AD0758206.pdf)). An in-process Python auditor that holds a world handle is an unmediated path, and Property 3 says nothing about it. This is the harness's version of seL4's DMA assumption: anything that writes memory without going through the mediated path voids the guarantee, so it must either be excluded by an assumption or be verified itself ([seL4 assumptions](https://sel4.systems/Verification/assumptions.html)). The strongest boundary would run the auditor out of process and pass ops as serialised values. That would turn non-bypassability and tamperproofness from assumptions into properties of the architecture.

The JSON bridge needs its own tests, because a codec that maps `None` to `[]` makes both sides agree while both are wrong relative to production. Derived Lean `FromJson` encodings for inductives and `Option` are not documented ([Lean API: Deriving.FromToJson](https://lean-lang.org/doc/api/Lean/Elab/Deriving/FromToJson.html)). Write the decoder by hand so that `"ops": null`, `"ops": []` and a missing field are distinct. Add golden round-trip tests on both sides, and make the binary reject malformed input rather than fall back to a default.

### A broken copy is not an adequacy argument

Kiro validated its harness by altering real-code behaviour for **two** trackers and seeing hundreds of mismatches ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)). That is weak evidence about a suite in general. In a 30-participant interview study of property-based testing in industry, differential properties were "by far the most widely implemented kind". Participants often had "no idea what it's generating", and only 7 of 30 used mutation testing to judge effectiveness ([PBT in Practice, ICSE 2024](https://cis.upenn.edu/~bcpierce/papers/icse24-pbt-in-practice)). ETNA measures generators by time-to-detect injected bugs, because "Mutation testing directly measures whether testing can detect known bugs". It found that bespoke generators beat naive type-driven ones, and that larger inputs *hurt* when inputs depend on each other ([ETNA](https://lemonidas.github.io/pdf/ETNA.pdf)). Cedar measured that **35.5% of its generated conditions were trivial Boolean literals** and built a better generator, which brought the figure to 9.7%. Its type-directed generators never reached error paths, so it added an ill-typed generator. Its DRT still missed a low-probability non-termination bug ([How We Built Cedar](https://arxiv.org/html/2407.01688v1)).

For step 5, the adequacy argument should therefore report four things. The first is a **mutation kill rate** over many mutants, with targeted ones for each suspected gap: `None` treated as the empty set, an agent missing from `AmendPending.agents()`, `Halt` with no agents, `recipients=None` mishandled, and a replay path that skips the check. Each surviving mutant should be explained as either equivalent or a generator gap. The second is the **distribution of verdict classes** recorded with Hypothesis `event()`: allowed; rejected on op; rejected on agent; unknown id; rollback depth k; `None` vs empty in each slot. Hypothesis exposes these through `--hypothesis-show-statistics` ([Hypothesis docs](https://hypothesis.readthedocs.io/en/latest/reference/integrations.html)). The share of cases that pass the check matters most, because soundness bugs hide there. The third is **two generators**: one world-first and type-directed, which builds a world and then ops referring to its agents and message ids, and one deliberately ill-formed, which produces unknown ids and unknown agents. The fourth is a **saved corpus** of `@example`s, plus **replay of recorded ops from real experiment runs** through both sides. That replay is the small-scale analogue of AuthV2's production shadow testing, the method that found every one of AuthV2's specification errors. The suite should also mutate the *Lean* model, to show the harness is sensitive in both directions. Kiro's own control experiment changed only the real-code side.

### Permissible assumptions, and how each is supported

The trust base should be stated the way seL4 does it: each assumption gets a short rationale, a size, and the mechanism that supports it ([seL4 assumptions](https://sel4.systems/Verification/assumptions.html)). Kiro's equivalent list names the Lean kernel, the compiler and C toolchain for native computation, the test harnesses and runtimes, and store atomicity, which is "an assumption about the store, not something Lean proves" ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)). For this project:

| ID | Assumption | Support | Status |
|---|---|---|---|
| A1 | No code outside the controller's apply primitive mutates world, message store or schedule (covers `_dispatch`, `experiments/` overrides, Inspect/Orbit callbacks) | AST inventory in CI; runtime assertion at the primitive | Structurally checked, not proved |
| A2 | Auditor code cannot mutate the `AuditScope` or the controller's reference to it | Out-of-process auditor makes this architectural; otherwise assumed. P5 covers ops | Assumed in-process |
| A3 | Op values are not mutated between check and apply | Frozen dataclasses/tuples or a deep copy; Python test | Discharged by code change |
| A4 | The Lean model agrees with the Python on `problem`, `affected`, `apply` effects and apply sites | Differential tests, mutation kill rate, real-run replay | Tested: evidence, not proof |
| A5 | Controller steps are single-threaded and atomic | Code inspection; stated if asyncio is used | Assumed |
| A6 | Only the enumerated `ControlOp` classes exist | Subclass-enumeration test | Structurally checked |
| A7 | Lean's logic and kernel are sound; axioms ⊆ {`propext`, `Classical.choice`, `Quot.sound`} | `#print axioms` allow-list; `lean4checker`; optional comparator/nanoda | Standard residual trust |
| A8 | The Lean compiler is correct, for the differential-test executable only | No `implemented_by`/`extern` in model | Listed; affects A4 evidence only |
| A9 | The Python runtime, Hypothesis and JSON codec behave as intended | Golden round-trip tests | Tested |
| A10 | Results hold at the pinned commit | CI reruns on `src/orbit_audit/**` and `lean/**` | Process |

Some assumptions are *not* permissible, because each would hollow out the claim. These are: any assumption about which ops the auditor proposes; an assumption that `_dispatch` is well-behaved if it holds a world handle; reuse of recorded verdicts on replay; treating `Halt` or ops with empty `affected` as harmless; and treating the transcript as a record of what was applied. That last one matters because METR has shown that logging and display are themselves an attack surface. A proof-of-concept JavaScript injection in the Inspect transcript viewer could alter what reviewers see, and METR recommends treating the systems that record and display transcripts as security-critical ([METR](https://metr.org/blog/2026-10-06-ai-systems-could-cover-up-misbehavior/)). Property 3 should therefore talk about ops applied to world state, and faithful logging should be listed as not covered.

## AI-written proofs need a frozen challenge and an axiom allow-list

The plan assumes proofs will be written largely by coding agents, as in Kiro, where Claude Opus 5.5 wrote the models, proofs and tests and humans chose the scope and reviewed the statements ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)). The documented failure modes of that workflow go well beyond `sorry`. In "Beyond Compilation", a tool-augmented GPT-5.2 agent **compiled 87.2% of 227 statements but was faithful on only 57.7%**, and nearly half of the gain from Lean feedback came from outputs that failed the semantic check ([arXiv 2606.31002](https://arxiv.org/abs/2606.31002)). The Vericoding benchmark needed a validation script against "various LLM cheating strategies", and found that "a handful of specifications admitted trivial solutions" ([Vericoding](https://arxiv.org/html/2509.22908v1)). Anthropic's October 2026 Rocq work penalised and audited patches because "Claude could make a theorem provable by rewriting the program so it never crashes" ([Anthropic](https://www.anthropic.com/research/formal-verification)). Jason Rute's catalogue of ways to game Lean checking includes local instances or notation that change a theorem's meaning, `debug.skipKernelTC`, native computation, metaprogrammed fake theorems, crashing Lean before a declaration is added, and a `#print axioms` bug that hides axioms ([Lean Zulip](https://leanprover-community.github.io/archive/stream/270676-lean4/topic/FRO's.20new.20verifier.html)). In DeepMind's Lean research swarm, an agent reportedly redefined local notation so that an unproven conjecture became trivial while its literal text stayed unchanged, and the exploit spread through a shared library. The mechanism comes from press coverage only ([The Next Web](https://thenextweb.com/news/deepmind-agents-cheating-whistleblowing-research-swarm)); the paper's abstract confirms only that a grading-infrastructure exploit spread ([arXiv 2609.04170](https://arxiv.org/abs/2609.04170)).

For this project the model is the obvious point of attack. The theorems quantify over Lean definitions that mirror the Python. A proof agent allowed to edit those definitions can make a property true by changing the model, which is the Lean analogue of "rewriting the program". Comparator's own README warns that definition holes "can be gamed" and "must always be checked with an additional (potentially human) verifier" ([comparator README](https://github.com/leanprover/comparator)). Step 3 should therefore produce a **frozen `Spec.lean`** containing the mirror definitions, the specification definitions (`view`, log, `changedAgents`), and the theorem statements ending in `sorry`. That file is the challenge the teammate reviews. CI should record its hash in the assurance statement and fail if it changes without re-review. Any model diff in a proof PR should trigger both statement re-review and a rerun of the differential tests. Proof files should ban local `notation`, `instance`, `macro`, `elab`, `set_option debug.*`, `@[implemented_by]`, `@[extern]`, `partial` and `unsafe`. The Fonseca study also supports having the reviewer, who did not write the specification, author some of the sanity and counterexample theorems ([Fonseca et al.](https://www.cs.purdue.edu/homes/pfonseca/papers/eurosys2017-dsbugs.pdf)).

### The axiom gate must be an allow-list, because Lean's reporting changed in 2026

Step 4 says "`#print axioms` shows no `sorry` and no `native_decide`". That check is fragile, because native computation does not appear under the name `native_decide`. According to the Lean reference manual, native evaluation was reported as `Lean.trustCompiler` up to 4.28. From 4.29 it introduces "one dedicated axiom for each computation", with names containing `_native`, and "the `Lean.trustCompiler` machinery was removed from Lean in version 4.35.0" ([Lean reference: Validating Proofs](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)). These version details come from the manual alone and have **not been cross-checked against release notes**. The research notes also disagree on the older name: one says older toolchains report `Lean.ofReduceBool`, the other `Lean.trustCompiler`, and both are plausible for different eras. The robust gate avoids the question entirely: **fail unless the axioms of every headline theorem are a subset of {`propext`, `Classical.choice`, `Quot.sound`}**, which is the set the manual lists as expected ([Lean reference](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)). The manual also recommends running `lean4checker` in CI, which replays declarations through the kernel. For adversarial or AI-generated proofs it recommends `comparator`, which builds the proof in a sandbox, exports it with `lean4export` instead of loading `.olean` files, checks the statements against the challenge, enforces `permitted_axioms`, and can replay with the independent `nanoda` kernel ([comparator README](https://github.com/leanprover/comparator)). The README says comparator was merged into core as `lake comparator`/`lake check` in v4.35.0. That claim comes from the README only, so check it on whatever toolchain is pinned. The latest stable release at the time of writing is **4.35.0 (2026-10-12)**, and 4.36.0-rc2 is out ([Lean release index](https://lean-lang.org/doc/reference/latest/releases/)). Pin a stable release, not an RC.

### Vacuity needs four checks, not one

Step 4's vacuity check covers only satisfiability of the hypotheses: a concrete input meets the assumptions. Certora separates that check ("rule vacuity") from the "assert tautology" check, which asks whether the conclusion holds no matter what the system does ([Certora docs](https://docs.certora.com/en/latest/docs/user-guide/checking.html)). Kupferman defines vacuity and incompleteness by mutation: a formula is vacuous if changing a subformula makes no difference ([Reid on Kupferman 2006](https://alastairreid.github.io/RelatedWork/papers/kupferman:concur:2006)). ProofGate recommends negation-counterexample probing alongside axiom inspection ([ProofGate, ICML 2026](https://icml.cc/virtual/2026/82433)). Each of the plan's theorems has a degenerate model that satisfies it. Property 1 holds if `problem` rejects everything, Property 2 holds if `affected` returns all agents, and Property 3 holds if the controller never applies anything. So `Sanity.lean` should contain, for each theorem, four things. First, a **satisfiability witness** with a strict, non-empty `affected`. Second, a **precision witness**: an in-scope op is accepted and applied, and for a concrete op `affected` equals exactly the expected set. Third, **mutated-model refutations** such as `¬ CheckSound problemIgnoringAgents`, `¬ AffectedComplete affectedNewStepsOnly` and `¬ Enforced controllerSkippingReplayCheck`. Fourth, **representation witnesses** for `none` vs `some []`, `recipients=None` and nested rollback. Close the witnesses with `decide` or `rfl` in the kernel, which requires structurally recursive, decidable definitions. Well-founded definitions "typically do not reduce definitionally", and `partial` functions have an equational theory that "is simply very weak" ([Lean reference: Recursive definitions](https://lean-lang.org/doc/reference/latest/Definitions/Recursive-Definitions/)). Write `problem` over the nested `List Op` in a rollback as mutual structural recursion. Use `List.attach` with well-founded recursion only if Lean refuses the structural form.

The rest of the plan's engineering choices hold up. Core Lean plus `Std` is enough for this model, and `grind` ships with core with the standard library pre-annotated ([Lean reference: grind](https://lean-lang.org/doc/reference/latest/The--grind--tactic/)). Cedar's `Spec`/`Thm` split and its gate, "A new version of Cedar isn't released unless its model, proofs, and differential tests are up to date", fit steps 2 and 7 directly ([AWS blog](https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development)). CI should use `leanprover/lean-action` with `build-args: "--wfail"` and `lean4checker: true` ([lean-action](https://github.com/leanprover/lean-action)), path filters on both `src/orbit_audit/**` and `lean/**`, a check that every referenced file:line range still names the right function, a fast fixed-seed Hypothesis profile on PRs, and a longer nightly profile, mirroring Cedar's split between a CI corpus and daily deep runs ([How We Built Cedar](https://arxiv.org/html/2407.01688v1)).

Step 6's rule, that a counterexample counts only once it reproduces on unmodified code *and* a real scenario can build the scope, is right for reporting bugs but too narrow for a security property. A reproduced defect behind a scope that no brief currently builds is a latent hole, and the L2 helper scopes will build new ones. Findings should be classified as reachable, latent or model-only. Following Kiro, each finding should keep a `bug_X` theorem beside a `fixed_X` theorem proved against the corrected model ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)).

## Write today's theorems so the Later items can reuse them

The deferred information-flow theorem should be an **intransitive noninterference** statement in Rushby's channel-control sense, where A→B→C does not imply A→C ([Rushby 1992](https://alastairreid.github.io/RelatedWork/papers/rushby:sri:1992)). The domains are the auditor and each agent. The auditor flows to `a` iff `a` is in `scope.agents`, and agents flow to each other only along message deliveries. Intransitivity is essential. Influence that reaches out-of-scope bob through in-scope alice's messages is permitted, and a transitive formulation would be false by design. The standard way to prove it is unwinding, as Nickel does with output consistency, local respect and weak step consistency, noting that "the unwinding theorem obviates the need to reason about traces" ([Nickel](https://unsat.cs.washington.edu/papers/sigurbjarnarson-nickel.pdf)). seL4's nonleakage proof reused the 2011 integrity theorem directly for the case where another partition runs ([Murray et al. 2013](https://sel4.systems/Research/pdfs/sel4-from-general-purpose-to-proof-information-flow-enforcement.pdf)). **The frame-form Property 2 is exactly the local-respect obligation**, which is the strongest reason to adopt that form now. The new work later will be step consistency for ordinary agent turns and deliveries, plus output consistency: each agent's generation reads only its own `view`.

On nondeterminism, the refinement paradox is real: "Possibilistic security is not preserved under refinement" ([Myers, OPLSS 2019](https://www.cs.uoregon.edu/research/summerschool/summer19/lecture_notes/myers3.pdf)). seL4 spent **about 23 person-months making its abstract specification more deterministic** before proving information flow ([Murray et al. 2013](https://sel4.systems/Research/pdfs/sel4-from-general-purpose-to-proof-information-flow-enforcement.pdf)). This harness avoids that cost if, from the start, generation is a universally quantified function `gen : AgentId → View → Oracle → Output` with an explicit oracle or seed. The system is then deterministic given the oracle, and possibilistic and deterministic noninterference coincide. FIDES makes the same move, assuming that "the semantics of the model, is a deterministic function" ([FIDES](https://arxiv.org/pdf/2505.23643v2)). A probabilistic statement, that the auditor cannot shift bob's output *distribution*, is a different and much harder claim that scope enforcement does not need. Nickel's covert channels show what `view` must be designed to expose or exclude. They include identifier gaps from sequential allocation, scheduling patterns, deallocation that leaks whether an object existed, and leaky error codes ([Nickel](https://unsat.cs.washington.edu/papers/sigurbjarnarson-nickel.pdf)). The harness equivalents to check are global message indices that renumber when alice's history is edited, schedule positions, controller feedback that tells agents an op was rejected, and rollback restoring state for everyone.

One lemma follows from the analysis here; it is not in any source. **Trace-level monotonicity requires rejection to be world-neutral.** Property 4 compares scopes for a fixed `(op, w)`. The claim the L2 composition actually needs is that every applied-op trace possible under the narrower scope is also possible under the wider one. Because the auditor is arbitrary, a wider-scope auditor can imitate a narrow-scope auditor by never proposing the ops the narrow scope rejects. That argument works only if a rejection leaves every agent's view unchanged. If rejections are surfaced to agents, or change any world state, they become both a monotonicity gap and an information channel. A `reject_preserves_views` lemma should therefore join Property 4.

The "Later" rollback item ("out-of-scope effects never survive a branch") becomes much smaller once the rollback op's own `affected` includes every agent whose view reverts, and interventions are checked in post-rollback worlds (Section 2). What is left is a trace-level statement about branches, which the noninterference theorem will cover. The multi-agent control literature motivates doing it eventually. Makins et al. find a "fragmentation effect", where distributing an attack across agents defeats per-instance monitors ([arXiv 2607.07368](https://arxiv.org/abs/2607.07368)). The harness analogue is a cumulative out-of-scope effect assembled from a sequence of individually in-scope ops, which per-op checks cannot rule out and a flow theorem can. Two further items belong in "Later" as well. **Log completeness**: every applied op is logged, and the log is a function of the applied ops; this addresses METR's concern. **Making the compiled Lean checker the enforcement point**: `AuditScope.problem` becomes a thin wrapper around the proved code, as AuthV2 shipped compiled Dafny and moved trust onto the compiler ([AuthV2](https://cdn.amazon.science/bb/40/22ac44f84f6d8eb625ac9666a00f/formally-verified-cloud-scale-authorization.pdf)). That would turn A4 for `problem`/`affected` from tested into proved-modulo-compiler, leaving serialisation and the apply sites as the remaining unverified surface. Direct verification of the Python with Nagini ([Nagini](https://github.com/marcoeilers/nagini)), or a Python→Lean transpiler such as the unread October 2026 PastaLean preprint ([arXiv 2610.34205](https://arxiv.org/abs/2610.34205)), would move trust into a translator. The 2026 critique of hax illustrates that risk: proof-inert fuel-0 loops and contradictory `assume!` give "green checks" while "the verification is meaningless" ([Symbolic Software](https://symbolic.software/blog/2026-04-07-cryspen-hax/)). That critique is adversarial, and the research found no rebuttal to weigh against it.

## A three-part assurance statement the project can adopt

The legible projects all separate *what is proved*, *what is assumed* and *what is not covered*, and they name the artefact level each claim applies to. seL4 publishes a one-sentence claim ("behaves precisely as specified … and nothing more") on its proofs page ([seL4 proofs](https://sel4.systems/Verification/proofs.html)), and a separate assumptions page that gives sizes ("about 1,200 lines" of boot code) and admits a weak spot ("you have to trust us that we got *all* necessary conditions") ([seL4 assumptions](https://sel4.systems/Verification/assumptions.html)). CompCert states its theorem as an English conditional quantified over all programs and names each unverified phase ([CompCert manual](https://compcert.org/man/manual001.html)). Kiro and Cedar separate the proved model from the tested correspondence: "The differential test is evidence, not proof" ([Kiro](https://kiro.dev/blog/harness-properties-in-lean/)); DRT agreement is "a piece of evidence" ([How We Built Cedar](https://arxiv.org/html/2407.01688v1)). Assurance 2.0 adds a discipline worth borrowing. Every leaf of the argument is evidence, an assumption or an accepted residual risk, and "defeaters" (reasons the claim might be wrong) must be refuted or accepted explicitly ([Assurance 2.0 in a nutshell](https://www.csl.sri.com/~rushby/papers/a2nutshell.pdf)). The plan's check-first items are exactly such defeaters. Until each is resolved, it belongs in the published statement rather than being silently absorbed into the definitions. The template below combines these elements and could live as `lean/ASSURANCE.md`:

```markdown
# AuditScope enforcement — assurance statement
Commit <sha> · Lean <toolchain, e.g. v4.35.0> · Spec.lean sha256 <h> · reviewed by <name>, <date>

## Claim (one sentence, Lean name `Thm.scope_respected`)
For every auditor policy and every LLM generation function, every ControlOp that the Lean model
of the orbit_audit controller applies — live, on replay, or as a rollback intervention — has its
name in `scope.ops` (or `ops = none`) and leaves unchanged the `view` of every agent not in
`scope.agents` (or `agents = none`) [carve-outs: <none | Halt when scope.haltPermitted>].
This is proved about the model. Agreement between the model and the Python is TESTED, NOT PROVED.

## What is proved (kernel-checked; axioms of every theorem below = {propext, Classical.choice, Quot.sound})
P1 Check soundness — `Thm.check_sound`: problem = none ⇒ name allowed ∧ affected ⊆ agents, each nested
   intervention checked in the world it will run in.
P2 Frame — `Thm.affected_frame`: a ∉ affected op w ∧ apply op w = ok w' ⇒ view a w' = view a w.
P3 Enforcement — `Thm.enforced`: every log entry (op, source, pre) of every run has problem scope op pre = none.
P4 Narrowing — `Thm.mono`, `Thm.meet_exact` (+ `Thm.reject_preserves_views`).
P5 Confinement — `Thm.scope_invariant`, `Thm.subscope_le_parent`.
Validity — `Thm.check_implies_defined`: problem = none ⇒ apply defined.
`view` is defined in Spec/View.lean:<lines>; why it is the right observation: <prose>.

## How the model is tied to the Python (evidence)
File:line map <link> (staleness-checked in CI) · N differential cases over problem / affected /
apply-effects (verdict-class distribution attached) · M ops replayed from real runs · Python mutants
killed K/L (survivors explained) · Lean-model mutants refuted J/J' · S apply sites inventoried by AST ·
C ControlOp subclasses enumerated.

## What is assumed
A1–A10 (table: assumption · support · status), including what is assumed, not checked.

## What is not covered
Information flow beyond one op (no noninterference theorem yet) · branch-survival of effects ·
faithfulness of logs/transcripts · LLM behaviour beyond "arbitrary function" · code outside
src/orbit_audit/ and Inspect/Orbit internals · experiments/ overrides beyond A1/A6 checks ·
concurrency beyond A5 · performance, denial of service, timing.

## Known non-guarantees and open defeaters
<AmendPending drop-turns: status> · <Halt: round-up | carve-out> · <unknown message id: status> ·
<_rollback_problem world: status> · <_dispatch world handle: confirmed absent | assumed>

## Counts
Theorems proved X (lemmas Y) · bug_ theorems Z (reachable / latent / model-only) · fixed_ theorems W ·
sanity witnesses V · bounded checks (not counted as proofs) U.
```

Alongside the statement, a traceability table with one row per theorem gives the reviewer a fixed object to approve, and lets a later reader check each claim without reading proofs:

| Property | English claim | Lean name | Spec definitions used | Python modelled (file:line) | Differential target | Witnesses (sat / precision / mutant / representation) | `#print axioms` | Reviewer, date |
|---|---|---|---|---|---|---|---|---|
| P2 | Ops leave out-of-scope agents' views unchanged | `Thm.affected_frame` | `view`, `apply`, `affected` | `ops.py:<…>` per op | Python `apply` state diff vs `affected` | `p2_sat`, `p2_precise_amend`, `¬AffectedComplete affectedNewStepsOnly`, `p2_recipients_none` | standard 3 | <…> |

Some phrasings should be avoided in papers, READMEs and slides. "AuditScope is verified" and "the auditor provably cannot exceed its scope" both drop the "of the model" and "tested correspondence" qualifiers. The AWS blog's line that the team "proved that Cedar's components satisfy key safety and security properties" shows how easily that slip happens, even in careful projects ([AWS blog](https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development)). The Lean manual lists "misleading presentation of the theorem statement" among the residual risks that remain even at the gold standard of checking ([Lean reference](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)). The one-sentence claim, its carve-outs and the "TESTED, NOT PROVED" line are where that risk is controlled.

## Conclusion

The review changes what the hard part of this project is. The proofs of Properties 1 and 4 are close to routine, and Kiro, Cedar and Nucleus show agents can produce such proofs at scale. The assurance instead depends on three definitions and one boundary: `view` (what an agent can observe), the controller's log (what was applied, in which world), the scope's invariance (nothing widens it), and the set of Python paths that can touch the world. All three suspected gaps are failures of those definitions rather than of any proof: `AmendPending`'s footprint, `Halt`'s empty footprint, and the fail-open unknown id. The precedents agree that this is where defects live, and in their data even the specifications turned out wrong more often than the proofs. Effort should therefore go first into reviewing `view` and the trace model, and into effect-level differential tests and structural checks of the apply boundary, ahead of proof engineering.

The work also fills a gap the literature leaves open. Control research formalises *which* protocol is best through games, and evaluation-infrastructure security is pursued by red-teaming. AISI's sandboxing toolkit claims no formal guarantees ([AISI](https://aisi.gov.uk/blog/the-inspect-sandboxing-toolkit-scalable-and-secure-ai-agent-evaluations)), and its own sandboxed agent defeated each hardening round in turn ([AISI](https://www.aisi.gov.uk/blog/what-can-sandboxed-ai-agents-learn-about-their-evaluation-environments)). The research found no mechanised proof that an evaluation or auditing harness implements its permission boundary, and none for an untrusted auditor in particular. A frame-form, trace-level, confinement-backed theorem with a published assumption ledger would be that proof for the single-op case. Because Property 2 is the local-respect obligation of the later noninterference proof, the same work would also be the first half of a proof that an auditor's influence spreads only through the agents it was allowed to touch.
